# Platform API v1

The bearer API under `/api/v1` lets an app call Platform with the OIDC access token of a Platform admin, such as LibreDB Mobile after its sign-in.
It exists in self-hosted mode only: cloud mode signs in with a password and has no OIDC issuer.
`PLATFORM_API_AUDIENCE` turns it on, and `docs/deploy/platform-runtime.md` lists it with `PLATFORM_API_CLIENT_IDS`.
With the API off, every `/api/v1` route answers 404 `API_DISABLED`.

## Authentication

Every request carries `Authorization: Bearer <access token>`, and no route reads the session cookie of the web console.
The token is a plain OIDC access token, checked with standard JWT rules against the keys that the `jwks_uri` of `${AUTH_KEYCLOAK_ISSUER}/.well-known/openid-configuration` names:

- an asymmetric signature (RS, PS, ES or EdDSA), never `none` or an HS algorithm;
- `iss` equal to `AUTH_KEYCLOAK_ISSUER`;
- `aud` holding `PLATFORM_API_AUDIENCE`;
- `azp` among `PLATFORM_API_CLIENT_IDS`;
- `exp` present and `nbf`, when present, with at most 30 seconds of clock skew;
- `sub` and `email` present;
- the role claim `PLATFORM_ROLE_CLAIM` holding `PLATFORM_ADMIN_ROLE`, the same rule as the web sign-in.

The caller is always a Platform admin of the install tenant with every permission, the same user a Keycloak web session gets, and a caller never names a tenant.
The first call of an account provisions its Platform user and takes an admin seat exactly as its first web sign-in does, so the license can refuse it.
An app takes Platform's rights from `GET /api/v1/me`, never from the claims of its token.

Unlike a web session, a bearer request is not rechecked against the Keycloak directory.
That recheck exists to end a long-lived cookie session, and the short lifetime of the access token ends a bearer's access instead.

One token serves Studio and Platform: the mobile client's access token carries both audiences, `libredb-studio-api` and `libredb-platform-api`.
Studio could therefore replay an admin's token to Platform within its lifetime.
This release accepts that, because only a token of an account with the admin role passes, that account can do the same in the web console, and the access token is short-lived.

## Errors

Every error answers with the body `{ "error": { "code": "<CODE>", "message": "<text>" } }`, and no message carries the token or a claim value.

| Status | Code | When |
| --- | --- | --- |
| 401 | `BEARER_INVALID` | No bearer token, or one whose signature, issuer, audience, client, lifetime or claims fail; the answer carries `WWW-Authenticate: Bearer error="invalid_token"`. |
| 403 | `ADMIN_ROLE_REQUIRED` | A valid token whose role claim lacks the admin role. |
| 403 | `LICENSE_ADMIN_SEATS`, `LICENSE_EXPIRED`, `LICENSE_INVALID` | The first call of an account, when the license refuses its admin seat. |
| 503 | `IDENTITY_PROVIDER_UNAVAILABLE` | The keys of the issuer cannot be read; never a 401, so an app does not sign its user out over an outage. |
| 404 | `API_DISABLED` | Cloud mode, or `PLATFORM_API_AUDIENCE` unset. |
| 400 | `VALIDATION_FAILED` | Invalid input; the error also carries `fieldErrors`, the messages of each field. |
| 500 | `INTERNAL_ERROR` | Any other failure, logged by Platform. |

Any other refusal of a route answers with its own code and status, such as 404 `NOT_FOUND`.

## Endpoints

### `GET /api/v1/me`

The caller's Platform user, its rights and the install tenant.

```json
{
  "id": "<users.id>",
  "email": "alice@example.com",
  "name": "Alice",
  "roles": ["PLATFORM_ADMIN"],
  "permissions": ["connection.view", "..."],
  "tenant": { "id": "<tenants.id>", "name": "Acme", "slug": "default" }
}
```
